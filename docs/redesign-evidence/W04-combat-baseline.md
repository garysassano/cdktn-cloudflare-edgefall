# W04 combat accounting and checkpoint/journal evidence

The four-browser combat laboratory now uses protocol 3.1. Its full baseline retains encounter completion, member resolution/kill attribution and allocation cursors after the corresponding enemies and transient events disappear. A separate validated server checkpoint and applied-input journal reconstruct the private combat continuation. An owned SQLite Durable Object proves storage transaction rollback and restoration after a fresh workerd process starts. Production remains v2; the continuously running WebSocket room does not yet persist through this store.

## Implemented boundary

The new binary combat section adds 144 bytes for the current four-player/two-target fixture. It has explicit table counts, policy/status/timestamp encodings and a maximum of 8,784 bytes; the full frame cap is now 47,896 bytes. Independent Python-struct goldens cover pending/completed sections. Unknown versions/flags, malformed/truncated sections, contradictory kill credits and reused allocation cursors fail before the snapshot is exposed. An encounter can complete while the campaign remains playing. See [snapshot contract](../snapshot-v3.md).

The checkpoint preserves full target bodies, patrol turns, encounter receipts/watchdog continuation, action/marker/allocation cursors, current notices, output event history, acknowledgments and the connected input-owner roster. Journal segments retain the normalized input actually applied, edge outcomes and external disconnect/stale decisions. Reconstruction checks every contiguous prior/result hash and reproduced outcome. The SQLite transaction advances checkpoint/segment data and the durable head together, with bounded retention. See [archive/storage contract](../combat-checkpoint-v2.md).
