# W04 running combat persistence and recovery

The diagnostic combat room now writes its accepted input journal while four real browser clients play. One bounded writer serializes SQLite commits, pauses on failed persistence or thirty unconfirmed ticks, and reconstructs a valid durable prefix before issuing replacement input/output generations. A fresh workerd process and two controlled storage-failure scenarios pass. Production remains v2; this is the existing firearm/encounter laboratory, not complete campaign or production membership recovery.

## Implemented boundary

The coordinated world/input transaction captures its journal and every fifteenth accepted state before asynchronous work. Storage validates the hash chain and accepted boundary without running the simulation again during the write. Archive loading still resimulates the applied decisions and compares outcomes and hashes. The old write path ran the same fifteen ticks twice; removing that work avoids blocking the live room's event loop with redundant simulation. [Archive and writer contract](../combat-checkpoint-v2.md).

The writer distinguishes accepted ticks from confirmed durable ticks. Its maximum backlog includes the single in-flight segment and queued decisions. Write failure or reaching the thirty-tick limit closes the controlling cohort and stops the clock while preserving the tick already accepted. Late confirmation cannot resume gameplay. Recovery discards uncommitted queued work, reconstructs storage, and persists fresh run/control/connection epochs before sending baselines. The preserved simulation includes current action/marker and allocation cursors, weapons, projectiles, private enemy continuation and encounter/kill accounting. Four fresh connections and five preloaded commands per player are required before the persisted start barrier permits ticking.

## Preserved failures and observability

The first live-writer attempt rejected slot 0's commands 39–41 at server tick 34 for exceeding the unchanged six-tick lead limit. The tick-30 write was followed by a 92 ms timer gap and catch-up callbacks; synchronous world-step samples themselves were only a few milliseconds. Storage had committed through 30 and neither the world evaluator nor writer had failed. The write path then performed two full replay passes per segment; the accepted-state capture removes those passes while retaining replay validation on load. Local preparation/confirmation samples now include run epochs, and their elapsed durations are diagnostic rather than production CPU measurements. [Failed room](./W04-combat-writer-input-failure.json.gz), [client timelines](./W04-combat-writer-input-failed-clients.json.gz), [host/browser diagnostics](./W04-combat-writer-input-diagnostics.json).

A later event-baseline regression exposed a separate fault-injection bug: dropping the first entry of a replayed batch could remove an already consumed duplicate and create no gap. The injector now removes the next unconsumed event while retaining a later event, so consumer repair is actually required. While the old injector waited, the runtime clock regressed at tick 495; its persistence preparation/confirmation sample includes a negative elapsed value. Independent Node samples also show backward wall time while monotonic time advances. The durable head was 495, with no backlog or persistence/world failure. This remains a failed timing run, and the scheduler guards are unchanged.
