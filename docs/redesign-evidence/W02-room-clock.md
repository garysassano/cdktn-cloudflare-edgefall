# W02 room-clock foundation

Status: the bounded scheduler and local Durable Object timer lifecycle are implemented. W02 remains open for content compilation, renderer stress, representative world/codec workload, four-client observation, recovery/storage pressure and authorized staging cadence/cost evidence. The production v2 room does not yet use this clock.

## Scheduler contract

`src/worker/runtime/room-clock.ts` owns one asynchronous timeout through an injected timer port. It advances the world by consecutive integer ticks at a candidate 60 Hz; the world callback receives no timestamp or variable delta. Deadlines are anchored to the start of the current active period, avoiding accumulated floating-point error from repeatedly adding `1000 / 60`. Pausing cancels the timer; resuming starts a new deadline without simulating the time spent paused. Repeated starts are idempotent, and callbacks queued before cancellation or already executed cannot advance or disarm a newer clock.

Each callback reads time once, executes at most four steps and yields for at least one millisecond. More than 250 ms of debt causes recovery before any combat step. This deliberately strengthens the plan's illustrative pseudocode, which checked debt after catch-up: players should not suffer several stale combat steps before the scheduler acknowledges an excessive interruption. Compare the observed timestamp with `deadline + 250`, rather than comparing a rounded subtraction with 250, so the exact boundary is accepted. Missing time, time regression, counter exhaustion, timer failure, a throwing/asynchronous world step or observer failure also stop the clock. Recovery requires an explicit confirmed world tick after the fault callback returns; a failed tick is never acknowledged or retried automatically against potentially mutated world state. Terminal closure cannot be resumed.

The clock retains no history or storage. Its room adapter must enforce connection leases, neutralize stale input, persist paused/recovery states, reconcile clients and own the separate durable cleanup alarm. A synchronous tick may stop or close the clock when its world reaches an empty or terminal state; the completed tick remains acknowledged, with no subsequent catch-up step. The scheduler does not promise rollback of failed world mutations or persistence of its process-local deadline.

## Evidence

`test/runtime/room-clock.test.ts` contains 16 cases, including a simulated six-hour sequence with integer millisecond samples, catch-up bounds, the exact debt boundary, pause/restart cancellation races, duplicate callbacks, time faults, uncertain world-step failure, asynchronous adapter rejection, terminal/empty transitions and counter exhaustion. The six-hour case tests deadline arithmetic and timer ownership using an injected clock; it is not a six-hour real-time soak or a memory plateau measurement.

`pnpm bench:room` launches and shuts down its own local Wrangler/workerd process and a separate diagnostic Durable Object. It checks TCP port availability, process health, stable object identity, bounded samples and monotonic ticks. Two active segments each complete 120 ticks and stop themselves. Independent Node HTTP observations then verify no progression or active timers during pause, a resumed segment is explicitly stopped mid-run, terminal closure removes all timers and a subsequent start is rejected. A ten-second watchdog bounds each active probe segment; it is also removed on pause/fault/closure. The probe has a cumulative 600-tick cap and a 2,400-sample cap. It accepts only loopback hostnames and is absent from the production Worker entrypoint and configuration.

The [recorded local trace](./W02-room-clock-proof.json) contains independent observer timestamps, callback lateness/step samples, runtime/reference-machine metadata and a SHA-256 covering the scheduler, numeric bounds, probe, runner and Wrangler configuration. `baseCommit` identifies the checkout before these additions; the source hash identifies the actual tested worktree. The recorded run completed tick 246, observed no discontinuity and ended with zero frame timers and no watchdog. HTTP observation is not WebSocket input or snapshot latency evidence. Stopping timers does not prove actual hibernation/wake reconstruction; no storage is written by this probe.

`pnpm check` passes 125 tests across 13 files, content/asset validation, all TypeScript targets, browser/Worker builds and CDKTN synthesis. `pnpm types` succeeds with no production binding declaration changes.

## Remaining acceptance

Cloudflare documents that deployed `Date.now()` and `performance.now()` advance after I/O, while local timers can advance during CPU work. The local trace therefore cannot establish deployed timer precision or synchronous CPU cost. Active timers also prevent Durable Object hibernation, making the zero-timer states necessary but insufficient evidence of recovery behavior. [Cloudflare timing documentation](https://developers.cloudflare.com/workers/runtime-apis/performance/), [Durable Object WebSocket lifecycle](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).

Next, extend the diagnostic with four real WebSocket clients and W01-sized input/snapshot payloads, independent receipt timestamps, neutral/active/background/lease-expiry transitions, checkpoint pressure and reconstruction. Replace preliminary workload with the W03/W05 world before final acceptance. Prepare the remote room-hour cap, cost dimensions and abort thresholds before requesting any missing staging authorization. The plan's five-minute cadence windows, two-hour staging soak, six-hour release soak, p99 world-plus-encode CPU budget and snapshot-gap targets remain unproven. Content/editor and renderer feasibility remain part of W02; this scheduler work does not close them.
