## Captured failure and corrected behavior

The original room accepted tick 120, then received commands 122–124 forty milliseconds later while still at that tick. Four milliseconds afterward it rejected the complete 125–127 batch because its final command exceeded tick 126. The four queued commands and processed acknowledgment stayed unchanged. The client had only fully applied snapshot 117 when sending both batches; receipt of the separate mapping message for tick 120 did not establish a validated snapshot.

The send limit is `min(counterCeiling, validatedSnapshotTick + 6) - initialServerTick`. The initial offset comes from the issued handshake. Prediction's later command/application mapping does not grant extra admission credit. A new limit becomes usable only after snapshot identity, hash, mapping and reconciliation checks succeed. Room recovery resets the input object against the new issued baseline.

`InputCapture.takeBatch()` requires an explicit sequence limit. It removes only the eligible contiguous prefix of at most three commands, leaving the rest in order with their original tick, ownership, held intent and edge IDs. A forced flush bypasses batching delay while preserving the send limit and frame-token budget. A closed window consumes no frame token. A validated snapshot attempts to drain eligible commands; it does not produce input samples or advance simulation time. Stopping diagnostic input capture neutralizes unsampled intent and allows retained commands to drain on later valid snapshots.

This is conservative transport control: delayed snapshots can make commands wait. The existing 120-command and 180-prediction-tick bounds, stale-input policy, fresh-baseline requirements and clock-discontinuity handling continue to apply. No command is discarded or renumbered to conceal a backlog. This increment does not establish latency, controller feel or recovery acceptance under the full 50–150 ms RTT matrix.
