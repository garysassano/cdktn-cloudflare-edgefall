# W04 room phases and signed host commands

The combat laboratory now begins in a real lobby. The signed current host loads the room and starts its ready cohort; a former host, replaced socket or stale membership/run epoch cannot issue those commands. An empty room durably records where it paused, so reconnecting to an empty lobby returns to the lobby without starting unseen combat. This extends the [loading connection boundary](./W04-loading-connections.md). Production authority remains v2.

## Implemented behavior

| Room phase              | New member                  | Reserved member                                                     |
| ----------------------- | --------------------------- | ------------------------------------------------------------------- |
| `lobby`, `intermission` | May claim an available slot | May replace its connection within the reservation                   |
| `loading`, `playing`    | Rejected with `in-progress` | May reconnect within the reservation                                |
| `paused-empty`          | Rejected with `in-progress` | Restores the saved passive phase, or loading for interrupted combat |
| `completed`             | Rejected with `room-ended`  | May reconnect to results without resuming gameplay                  |
| `recovering`            | Retryable outage            | Retryable outage                                                    |
| `expired`               | Room ended                  | Room ended                                                          |

The ninety-second reservation is checked independently of phase. An expired slot taken by another profile advances its membership generation instead of recycling generation one, preventing an old socket close from evicting the newcomer. Host succession selects the oldest connected member by join ordinal; returning does not reclaim the role.

Host commands contain exactly an action, run epoch, connection epoch and membership epoch, with bounded positive counters. The request reader limits the body to 512 UTF-8 bytes and two seconds, including an incomplete stream whose cancellation never settles. The session view omits profile identities and is bounded to four members and 2 KiB. The gateway verifies the signed profile and overwrites the internal identity header. The room checks active socket ownership and host status before processing `load` or `start`, repeats those checks inside the synchronous checkpoint transaction, and checks again after write confirmation before installing the phase. Anonymous `/combat/start` cannot bypass that path. A changed fence during persistence requires recovery if the outcome cannot safely be installed.

Every active reader must acknowledge its fresh snapshot and preload input before start. Lobby, intermission and completed readers can acknowledge snapshots but cannot submit gameplay commands. Waiting connection replacement persists a fresh per-player connection epoch without advancing the world; completed reconnect after a cold process also rotates that epoch. The last completed-room disconnect schedules reservation expiry without attempting to pause or replay completed combat.

The [format 2 archive](../combat-checkpoint-v2.md) includes the private `pausedFrom` field in validation and hashes. Format 1 laboratory archives are rejected. This does not migrate production storage or change the 3.1 binary snapshot layout. `continue` and `rematch` decode and undergo host authorization but return `command-unavailable`; campaign reset, progression and publication semantics are still required.

## Retained failures and limits

The first phase browser attempt reached the playing takeover stage, then all four clients closed with `clock-fault`. Independent Node samples show backward wall-clock steps of 810 ms and 1,692 ms while monotonic time advanced. The later status request had already cold-restored loading at tick 60 in epoch 3; it does not retain the original fault subtype. This establishes observed host-clock discontinuities, not their underlying cause. [Failure](./W04-phase-clock-failure.json.gz), [clients](./W04-phase-clock-clients.json.gz), [clock samples](./W04-phase-clock-diagnostics.json.gz).

The first automatic-reconnect attempt failed during the deliberate slot-2 browser stall. Slot 0 submitted sequences 127–129 at server tick 122 and exceeded the unchanged six-tick input-lead limit. The room's clock was still running without a recorded fault, and the independent host samples contain no backward wall-clock step in that attempt. This is a separate input/runtime scheduling failure. A passing rerun does not resolve it or establish sustained timing acceptance. [Failure](./W04-phase-lead-failure.json.gz), [clients](./W04-phase-lead-clients.json.gz), [diagnostics](./W04-phase-lead-diagnostics.json.gz).

The added SQLite verifier initially compared a per-player kill array by object identity; its values matched. The assertion now compares the arrays structurally with the correct type. No runtime guard or storage behavior was changed for that assertion. [Derived failure notes](./W04-phase-failure-notes.json).
