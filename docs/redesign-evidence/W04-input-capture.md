# W04 — Independent input capture

The network laboratory now samples one command per independent 60 Hz client tick rather than producing commands when snapshots arrive. Snapshots restore/reconcile authoritative state. A bounded buffer normally emits batches of three commands at 20 Hz, flushes discrete edges on their capture tick when its token budget permits, and limits transport to 30 frames/second with burst 10. Automatic fire is held intent plus a retained fire-onset edge, not a message per shot. The existing pure scheduler moved to `src/shared/runtime/room-clock.ts` so the browser and diagnostic room share its unchanged 250 ms debt, catch-up and discontinuity guards.

Input capture preserves press/release edges between ticks, independently numbers all five action kinds, ignores repeat keydown events and keeps aliased controls held until every source releases. Jump, fire-onset, grenade, interact and vehicle-special can coexist without overwriting each other. Eight edges fit each command, the unsampled edge queue is capped at 64, and unsent commands at 120; overflow requires resynchronization without evicting captured history. Blur and visibility loss clear held and unsampled intent, while already captured commands retain their immutable identities. This is keyboard integration and a reusable source abstraction, not completed gamepad support.

The authoritative controller probe now sends a playing snapshot at tick 0 before scheduling the first tick. Clients accept a newer snapshot ID at the same tick and use that server-issued start boundary to start their independent clocks. The previous approach waited for tick 3, wasting half the six-tick input lead; [the failed startup run](W04-input-start-failure.json) and [its client receipts](W04-input-start-clients.json) preserve a resulting overlap/resync failure. The six-tick server lead limit is unchanged. Local pending prediction may additionally include commands captured since the last 20 Hz snapshot; it is not the same metric as queued server lead.

## Validation and current failure

302 unit tests across 29 files pass, including ten input-capture cases and the existing scheduler suite. [Node, Chromium and local workerd agree](W04-input-runtime.json) on capture trace `5e388510`: 60 commands, 21 frames including early edge flushes, two separate fire taps, simultaneous jump/grenade, and held release. This portable fixture uses ordered events between capture ticks and requires no snapshots to drive input. Existing controller prediction trace `9b62ab0c` is unchanged.

The initial `pnpm check` completed tests and wrote synthesized output but remained alive after a telemetry HTTP “Bad Gateway” response. The installed CDKTN CLI's telemetry handler rejects a non-success status before consuming its response body; the process retained an HTTPS connection. That owned process was terminated; `CHECKPOINT_DISABLE=1 pnpm check` then passed completely using the supported ephemeral setting. No dependency, global tool configuration or telemetry preference was changed.

The four-browser run with the server-issued start boundary reaches snapshot tick 144 with zero full-controller corrections in all four clients, then [fails on a runtime clock regression at tick 145](W04-input-clock-failure.json). [Client evidence](W04-input-clock-clients.json) records sequence 151, seven locally pending commands and one or two unsent commands at closure. The [inspected screenshot](W04-input-clock.png) shows the explicit clock-fault closure. This version does not have a passing complete network-verifier result: the nominal 10 ms simultaneous keyboard-action checks and extended lease phase occur later and were not reached. The earlier passing tick-422 report in W04-controller-prediction.md belongs to the snapshot-driven input version and is not substituted for this run.

The [independent Node host-clock samples](W04-input-clock-diagnostics.json) now overlap a real runtime failure. The last completed callback reports runtime time 1788726767993; the fault reports 1788726767204, a 789 ms regression. Node separately samples wall time 1788726768005 followed by 1788726767225, a 780 ms regression, while `process.hrtime.bigint()` advances by 24.163216 ms. Its next wall-clock sample regresses by a further 1,127 ms while monotonic time advances by 26.516985 ms. Thus the failure coincides with a host wall-clock step, not merely a stalled browser callback. A read-only `timedatectl` check reports NTP enabled and synchronized, but no timesyncd journal entries were available; that does not identify which host/hypervisor/time service changed the clock. No host clock settings were changed.
