# W04 — Controller prediction and four-browser room foundation

The opt-in network laboratory now runs four actual foot controllers over the compiled static LDtk terrain in an authoritative diagnostic Durable Object. Each Chromium context has its own WebSocket, input stream and full-controller predictor. Production gameplay remains v2; this foundation does not close W04/G2.

`ControllerPrediction` restores the full actor at the snapshot tick, removes processed commands, and replays only the remaining commands at their original mapped ticks. It preserves vertical motion, velocity remainders, shape, contacts, support, jump buffer, coyote time, action state and edge cursors. The acknowledgment's application tick is not mistaken for the snapshot boundary. Pending commands are bounded to 120 and prediction history to 180 ticks. Conflicting acknowledgments, reused edges, epoch/lifecycle/geometry changes and missing mapping stop prediction and require a fresh server input baseline. No held-state extrapolation or guessed remapping hides missing history. Server issuance of replacement baselines remains open work.

The controller workload uses the real compiled content and media digests, with explicitly local fixture simulation/deployment identities. It has no enemies, projectiles, vehicles or combat. Jump requests use the shared controller; multiple jump edges in one tick produce at most one applied jump. Combat edges are consumed as unavailable. The browser displays predicted and authoritative colliders with labelled engineering graphics. This is not final art or remote interpolation.

The network fixture preloads six command ticks using two three-command packets, within the existing maximum lead of six. During play, each 20 Hz snapshot triggers three further input commands. That bounded laboratory pump is not acceptance of the final independent input-capture cadence or its latency. Clock discontinuity, catch-up and 250 ms debt guards are unchanged.

## Evidence

`pnpm check` passes 292 tests across 28 files. `pnpm test:contracts` agrees across Node, Chromium and local workerd on the four-controller 180-tick trace `9b62ab0c`, including 240 full-state reconciliations, jumping and crouching: [runtime report](W04-prediction-runtime.json). The 1,416-byte snapshots describe a movement-only world and do not close the previously failing busy-room bandwidth gate.

The preserved [four-browser movement report](W04-controller-movement.json) passes through tick 180 with 60 shared snapshots, identical authoritative world hashes and no full-controller correction in any client. Each client retains six pending commands. The subsequent input-stop test [fails at tick 344](W04-controller-runtime-failure.json): runtime time regressed by 786 ms, causing guarded recovery. The stopped peer's held input was neutralized at tick 199 despite 53 acknowledgment-only frames, but lease expiry was not reached. [Client receipts](W04-controller-runtime-clients.json) and the [inspected screenshot](W04-controller-network.png) preserve the failure; the image shows the clock-fault closure, not a successful extended run.

An earlier six-tick-preload run likewise [failed at tick 244](W04-controller-clock-failure.json), after an approximately 691 ms clock regression. Its [client receipts](W04-controller-failed-clients.json) retain matching state through tick 243. An earlier [three-tick-preload failure](W04-controller-three-tick-failure.json) retained only a generic baseline error and does not establish its initial cause. No repeated-run selection converts these failures into cadence acceptance.

The verifier now clears its own prior reports at startup so a failed invocation cannot leave a stale pass. It records bounded independent Node monotonic/wall-clock samples and browser console/page/request errors in `diagnostics.json`. These diagnostics supplement the scheduler callbacks, timer requests/firings, input admission and lease metrics already captured. See [observability status](observability.md) for the distinction between local evidence and configured-but-not-deployed Cloudflare traces.

The first instrumented run reached tick 423 without a clock fault, but exposed an [assertion bug in the verifier](W04-controller-peer-order-failure.json): it assumed connection order matched slot order and inspected slot 1 instead of the stopped slot 0. The recorded slot 0 had actually expired at tick 367. Checks now identify peers by explicit slot. This cause applies to that assertion only, not the earlier runtime regressions. The [host samples from that run](W04-controller-host-clock.json) contain no backward wall-clock sample.

After that fix, the [complete short browser scenario passes](W04-controller-network-report.json) through tick 422 with peers arriving in order 2, 3, 0, 1. Slot 0 neutralizes at tick 199 and expires at tick 364 despite 60 acknowledgment-only frames; the other three remain active. The [inspected screenshot](W04-controller-network-pass.png) displays the expected slot 0 lease-expired closure. [Independent host/browser diagnostics](W04-controller-network-diagnostics.json) accompany the report. This one short passing scenario does not erase the captured clock regressions or establish long-running/live timing reliability. Correlating independent clocks during an actual regression remains unresolved.

Run with `EDGEFALL_CHROMIUM_PATH=/path/to/installed/chrome pnpm test:network:controller` when the installed browser is outside Playwright's expected cache revision. No browser download or package installation is required by the verifier. Reports identify the Chromium version and built client digest; their `baseCommit` is the checkout base at execution, before these changes were committed.
